# Final Submission Guide

This guide separates the prepared package from evidence that must come from the team's real run. The assessment PDF requires the problem statement, complete source code as text, and actual input/output screenshots with timestamps. Do not submit mock screenshots or treat this draft package as proof of a successful demo.

## Required order in each member PDF

1. Given project problem statement/question.
2. Complete source code as readable text. Include all project source, not only screenshots or excerpts.
3. Input and output evidence with timestamps. Capture the actual UI and API/database results after the PostgreSQL stack is running.

Include screenshots that demonstrate both Admin and Analyst login, a created dataset with fields/rules, upload of the sample CSV, validation issues and score, resolution history, and the database features. Add a visible timestamp to each captured screenshot or its caption. Capture the database view, stored procedure, trigger, constraints/indexes, and backup/restore results as direct terminal or database output.

## Files and upload destinations

- Upload the final PDF only to VTOP, using the individual member's name/registration number and the filename format above.
- Upload relevant PDF and DOC files to Moodle as the assessment brief directs.
- Keep the shared code package, README, schema, source listing, screenshots, and backup evidence with the team copy.
- Do not upload the `.env`, passwords, real institutional data, or a database dump containing private records.

## Ready-to-submit gate

Before upload, confirm that the final member copy contains the complete source listing and genuine timestamped evidence; the GitHub repository is private with all three collaborators, `main` and `dev`, and at least ten meaningful commits; the app has been run; the database backup has been restored successfully; and the live URL has been inserted if deployment is used. The code package alone does not satisfy these evidence and account requirements.
